# 一、项目背景

随着移动端设备性能不断增强，高端 Android 手机已经具备较强的本地计算能力。部分开发、预览、调试工作不再必须依赖 PC 与云端构建系统。

本项目希望构建一个完全运行在 Android 手机上的 UI 预览与动态 UI 执行系统，使开发者或用户可以直接在手机中：

1. 打开 Android UI 文件；
2. 实时预览 UI；
3. 编辑 UI 或代码；
4. 本地解析与渲染；
5. 在后续阶段本地编译动态 UI；
6. 在沙盒环境中运行动态 UI；
7. 全程无需 PC、云端或外部设备参与。

当前阶段优先实现的是：

> **Android UI 文件预览运行时**

也就是先保证：

```text
Android UI 文件
  → 解析
  → 构建 UI 树
  → 布局
  → 渲染
  → 预览
  → 错误提示
```

在预览能力稳定之后，再逐步引入动态编译、动态装载、沙盒隔离、AGSL 视觉增强等高级能力。

# 二、产品愿景

本项目的长期愿景是：

> 在 Android 手机上构建一个自包含、离线可用、可扩展、可预览、可执行、可沙盒隔离的动态 UI 引擎。

更具体地说，目标是让手机本身成为：

```text
UI 编辑器
UI 解析器
UI 渲染器
本地构建器
动态模块加载器
沙盒运行环境
视觉合成器
```

最终形成：

> **On-Device UI Foundry**  
> 端侧 UI 铸造厂

# 三、核心问题

本项目要解决的核心问题包括：

---

## 3.1 手机端缺少轻量 UI 预览能力

传统 Android UI 开发通常依赖：

- Android Studio；
- Gradle；
- PC 构建；
- 模拟器或真机部署；
- ADB；
- 云端 CI；
- 资源编译工具链。

这导致简单 UI 预览也需要较重的工作流。

本项目希望在手机端完成基础 UI 预览，降低反馈成本。

---

## 3.2 UI 修改反馈链路过长

当前常见流程：

```text
修改 XML / Kotlin
  → Gradle build
  → 安装 APK
  → 启动页面
  → 查看效果
```

本项目希望变成：

```text
修改 UI 文件
  → 手机本地解析
  → 手机本地渲染
  → 立即预览
```

---

## 3.3 动态 UI 需要安全运行环境

如果未来支持动态 UI 代码或动态模块，必须解决：

- 代码来源可信；
- 动态装载安全；
- 资源隔离；
- 能力控制；
- 崩溃隔离；
- 版本兼容；
- 主题一致性；
- 状态保存。

因此本项目不是简单的“加载文件”，而是要逐步建立完整的动态 UI 沙盒体系。

---

# 四、项目定位

本项目定位为：

> 一个运行在 Android 手机上的本地 UI 预览与动态 UI 运行时框架。

它不是：

- 完整 Android Studio；
- 完整 Gradle 构建系统；
- 通用 IDE；
- 应用商店动态更新框架；
- 任意 APK 插件化框架；
- 任意第三方 SDK 免审运行环境；
- 系统级 ROM 修改工具。

它是一个专注于：

```text
UI 文件
UI 预览
UI 渲染
UI 沙盒
本地动态 UI
```

的垂直系统。

# 六、总体目标

---

构建一个完全运行在 Android 手机上的 UI 预览与动态 UI 执行框架。

该系统应能够：

1. 读取本地 Android UI 文件；
2. 解析 UI 结构；
3. 解析资源与主题；
4. 渲染 UI 预览；

7. 支持后续动态 UI 扩展；
8. 支持本地编译与沙盒运行；
9. 支持高性能预览；
10. 支持可扩展架构。

---

## 6.2 当前阶段目标

当前阶段目标不是完整动态编译，而是：

> **先做出稳定可用的 Android UI 文件预览框架。**

当前阶段要完成：

```text
本地 Android UI 文件
  → XML / UI Node 解析
  → View 构建
  → measure / layout / draw
  → Bitmap / Compose 显示
  → 错误提示
  → 主题切换
  → 尺寸切换
```

---

## 6.3 长期目标

长期目标是实现：

```text
本地源码或 UI 描述
  → 本地解析
  → 本地编译
  → 本地打包
  → 本地装载
  → 沙盒执行
  → 原生渲染
  → AGSL 视觉增强
```

- 本地依赖仓库；
- 本地资源仓库；
- 本地沙盒运行时。

# 七、设计原则

---

## 7.1 Offline First

所有核心能力必须离线可用。

系统不应依赖：

- 网络下载；
- 云端编译；
- 云端渲染；
- 远程资源；
- PC 连接；
- ADB；
- 外部服务器。

---

## 7.2 Preview First

第一阶段必须优先保证预览能力。

任何架构设计都不能阻碍以下目标：

```text
打开 UI 文件
  → 快速看到预览结果
```

---

## 7.3 Incremental Complexity

系统复杂度必须分阶段引入。

不允许第一阶段同时处理：

- Kotlin 编译；
- DEX；
- ClassLoader；
- Compose Compiler Plugin；
- 动态资源；
- 沙盒进程；
- AGSL；
- 第三方依赖仓库。

这些必须后置。

---

## 7.4 Modular Architecture

系统必须模块化。

核心模块应可替换：

```text
UI Parser
Resource Resolver
Theme Provider
Renderer
Preview Surface
Diagnostics Engine
Sandbox Runtime
Compiler Engine
```

---

## 7.5 Safe by Default

动态内容默认不可信。

所有动态 UI、动态代码、动态资源都必须经过：

- 校验；
- 白名单；
- 签名或哈希；
- 能力限制；
- 错误隔离。

---

## 7.6 Deterministic Rendering

同一 UI 文件在同一设备、同一主题、同一尺寸下，应尽可能产生一致的预览结果。

---

## 7.7 High-End First, Graceful Degradation

优先面向高端 Android 设备：

- 强于或接近旗舰 SoC；
- 12GB+ RAM；
- 高速存储；
- 高刷屏；
- GPU 支持 AGSL。

但系统应具备降级能力：

- 低端设备关闭高级特效；
- 关闭实时编译；
- 关闭动态沙盒；
- 仅保留静态预览。

# 二十、风险与缓解

---

## 20.1 XML 兼容风险

风险：

- 不同控件属性复杂；
- 自定义 View 无法 inflate；
- 主题资源缺失。

缓解：

- 控件白名单；
- 资源 fallback；
- 错误诊断；
- 示例覆盖；
- 分阶段支持。

---

## 20.2 资源缺失风险

风险：

```xml
@drawable/xxx
@string/xxx
```

无法解析。

缓解：

- 第一阶段只支持字面量；
- 第二阶段支持宿主资源；
- 第三阶段支持资源包；
- 缺失资源显示明确错误。

---

## 20.3 渲染一致性风险

风险：

- 与真实 App 渲染不完全一致；
- 主题差异；
- window insets 差异；
- 字体差异。

缓解：

- 明确预览不是 100% 真机运行；
- 使用真实 LayoutInflater；
- 使用真实主题；
- 提供设备 profile；
- 后续引入更完整宿主环境。

---

## 20.4 动态编译风险

风险：

- Kotlin 编译器重；
- Compose 插件复杂；
- DEX 加载限制；
- ClassLoader 冲突；
- 内存压力。

缓解：

- 推迟到后期；
- 使用常驻编译器；
- 使用增量编译；
- 使用稳定 ABI；
- 使用内存 DEX；
- 使用签名 Bundle；
- 使用能力沙盒。

---

## 20.5 安全风险

风险：

- 恶意 XML；
- 恶意动态代码；
- 恶意资源；
- 越权访问。

缓解：

- 白名单；
- 签名；
- 哈希；
- capability；
- 进程隔离；
- 内存加载；
- watchdog。

# 二十五、结论

本项目的正确推进路径是：

```text
先做 Android UI 文件预览运行时
  → 再做资源、主题、编辑器
  → 再做 Compose 预览
  → 再做动态 UI Bundle
  → 再做本地编译
  → 再做沙盒与 AGSL
```

当前最重要的目标不是立即实现完整动态编译，而是：

> **先确保 Android UI 文件可以在 Android 手机上被稳定解析、渲染和预览。**

这是整个系统的地基。

一旦该地基稳定，后续的本地编译、动态装载、沙盒隔离、AGSL 视觉合成、完全离线 UI Foundry 才有可落地的基础。
